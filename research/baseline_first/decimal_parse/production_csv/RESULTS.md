DuckDB 1.4.3 imported 19,116 development rows into seven binary64 NumPy columns. All 133,798 present words matched Python Fraction converted to binary64. Both missing spellings (question mark and empty final field) produced SQL NULL and all 14 NumPy mask positions matched. No independent sample was opened.

The 13 full days had median import times between 1.428 and 1.821 ms each. The partial day took 1.002 ms. Each median covers ten imports after one warmup. The input is an anonymous Linux RAM file and the output is freshly allocated resident column arrays. Timing includes SQL binding, scanner setup, CSV parsing, result materialization and Python export. Schema and delimiter are supplied, date and time are projected away, and execution uses one pinned CPU and one DuckDB thread. These measurements cannot establish a kernel speed ratio against the preallocated C++ benchmark.

The pinned production scanner already converts a completed field directly into its typed output vector. Its DOUBLE branch passes a pointer and field length to TryDoubleCast, which calls fast_float on that range. This is direct typed materialization with general decimal conversion. The call path does not implement the candidate's combined delimiter recognition and three-fractional-digit kernel. This comparison establishes the implementation for DuckDB only. For a matched test, build two versions of the pinned DuckDB scanner with the same toolchain. Change only the numeric scanning path in one build, retain all CSV and null handling, and alternate imports through the same native query and result interface. Check every validity bit and present word before comparing paired timings.

Reproduce on Linux with Python 3.12, NumPy and the official duckdb==1.4.3 wheel. Run python run.py /path/to/prepared/days > timings.csv. The script selects the 14 development dates explicitly.
