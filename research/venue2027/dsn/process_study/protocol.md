# Prospective mechanism elimination study

This is an early stopping experiment for the DSN mechanism claim. It uses fresh process histories independent of the archived papers and the proposed large confirmatory matrix. Freeze this document in git before collecting any outcomes.

## Unit and schedule

Adapt the successful reservation → asynchronous PlaceOrder boundary from Beldi's public travel demo at commit 91280e1cfcadb5343c8d9320e0942414c06ce706. Represent a committed hotel/flight pair by one reservation and the immutable decision receipt by its operation/payload digest. Use synthetic resource IDs. The order table admits multiple orders per request so that duplicate delivery is observable. Both arms get the same stable request ID and payload on retry. This is a local port of the successful workflow slice. It omits inventory contention, identities, cloud infrastructure and upstream runtime performance. [Beldi frontend](https://github.com/eniac/Beldi/blob/91280e1cfcadb5343c8d9320e0942414c06ce706/internal/hotel/main/frontend/frontend.go)

Use an ephemeral isolated PostgreSQL 16.4 cluster with fsync and synchronous commit enabled. The source and order sink have separate transactions and connections. Kill the application worker with SIGKILL and start a new interpreter with fresh connections. The server survives. Per arm use one clean control and six kill points: inside the producer transaction; after the durable commit decision; before dispatch; inside the consumer transaction after the order insert; after consumer commit before source acknowledgement; after source acknowledgement. The candidate may have committed its effect marker before a sink transaction rolls back. Execute each schedule three times, alternating arm order by repetition. One operation per history, fresh state, one restart/replay for each arm (also replay the clean control), two deliveries at dispatch to exercise the independent consumer dedup key. Budget 10 seconds per worker including launch. Keep the exact cut, signal status, before/after observations, elapsed recovery time and every loss, ambiguity and timeout.

## Arms and observations

B1 atomically inserts reservation, decision receipt and pending message. The consumer inserts a unique processed ID and an ordinary order in one transaction. The relay acknowledges only after consumer commit. On restart scan pending records and replay the same client request idempotently. B3 materializes from an append-only intent/commit/outbox/effect chain following the repository candidate's ordering, reads and verifies the surviving journal, and replays missing materializations. Use the same consumer for both arms. Evaluate the unmodified B3 outcome fold, including its distinction between pending delivery and applied effect. Count claimed application only where the status explicitly asserts it.

A separate reader checks the durable operation key, payload, reservation, decision, pending/acknowledged message, processed ID and actual order multiplicity. Primary loss per history is any missing, duplicated, mismatched or unresolved joint outcome after replay. Secondary safety loss is an explicit claim of applied delivery while the sink lacks exactly one matching order at the stopped boundary. A pending message after a commit is permitted. A timeout or missing observation precludes a win. Elapsed time is descriptive, includes interpreter startup, and cannot rescue a safety tie. Deterministic schedules are coverage cases, not independent draws from a failure distribution.

## Binding decision

Advance only with a reproducible strict primary win against every matched baseline, no secondary regression, and a mechanism-level witness. A tie with B1 on the primary endpoint eliminates the DSN superiority claim. Stop before further baselines if B1 ties or wins. A win here would require subsequent comparison with a real durable-workflow engine. Beldi and Olive receive design comparisons only. No clinical, database-server-crash, power-loss, arbitrary-external-effect or general equivalence inference.

## Development repair after elimination

The two original runs tied on recovery and exposed premature application claims in the journal arm. Retire the original superiority claim under its registered rule. As a separate engineering question, retain both original arms and add a journal arm that writes EFFECT_APPLIED and the source acknowledgment in one source transaction **after** the idempotent sink commits. The old marker was written before delivery. Freeze the same schedules, three repetitions per arm, deadlines and independent observations. The repair succeeds only if it removes every observed premature claim and preserves exact recovery. A tie with the outbox still excludes a superiority paper.
