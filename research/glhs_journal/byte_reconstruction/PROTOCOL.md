This is a development comparison after the E16 audit. The earlier SGD cache studies already examined this file. Use every USER turn in every dialogue in the pinned Schema-Guided Dialogue training shard dialogues_001.json. For each USER turn the supplied payload is the canonical UTF-8 JSON object with one field "frames" containing the published frames, preserving list order and recursively sorting object keys. Exclude utterances. Use the zero-based dialogue and turn ordinal as the unique lookup key. The source is an external input to the readback workload, with no clinical interpretation. Store all snapshots before querying. Each arm may retain the complete canonical payload, durable per-snapshot metadata, and a per-dialogue archive. Query every key in each of three successive stages: after ingestion, after deleting all content for every dialogue whose ordinal is divisible by three, and after deleting all remaining content. Keep metadata throughout. Scope content addressing within a dialogue so revocation is effective even for duplicate content across dialogues. Disclose logical file bytes separately for content and metadata, without claiming identical storage footprint. Neither arm has access to the source file while answering. The independent checker reads source and actual output bytes in a separate process.

Candidate uses the repository's original GLHS v3 manifest validator and snapshot payload readback on restored manifests; storage/retention is a study adapter. Comparator signs a receipt binding lookup key, scope and content hash with Ed25519, verifies the receipt and the hash on retrieval. It stores the payload by content hash. Both use exactly the same copy and deletion rights. Missing, incorrect and exact payloads remain distinct. For expired reads, report returns as well as correct omissions. A case improves only if it recovers exact bytes that the other misses at equal allowed retention, or avoids an unauthorized return without losing authorized content.
