## 1. Executive Summary & Problem Formulation

In longitudinal clinical AI and clinical decision support systems (CDSS), an autonomous or human-in-the-loop LLM agent executes an asynchronous, non-deterministic inference pass over a bounded projection of a patient's electronic health record (EHR). The operational lifecycle of such an agent inevitably decouples into three distinct temporal coordinates:

1. **Read & Compilation ($t_1$):** The system accesses the underlying database, applies task minimization and patient consent filters, and compiles a governed disclosure snapshot $H$.
2. **Inference & Proposal Lineage ($t_2$):** The model receives a prompt payload derived from $H$, executes non-deterministic reasoning, and generates a structured mutation proposal $P$ (e.g., updating a medication regimen, revising an allergy list, or adjusting a care plan). In human-in-the-loop workflows, a clinician may review, adapt, or amend $P$ before final submission.
3. **Database Write Admission ($t_3$):** The proposed mutation $P$ is submitted to the transactional database for durable commit and persistence.

Between $t_1$ and $t_3$, both the patient's underlying clinical reality (concurrent clinician orders, lab releases, vital signs) and their governance directives (revocation of consent, updated institutional privacy policies, modified clinician credentials) can drift.

Existing literature provides sophisticated solutions for isolated segments of this pipeline:
- Relational databases provide **Optimistic Concurrency Control (OCC)** and **Serializable Snapshot Isolation (SSI)** to prevent dirty writes and detect write-skew over raw tuples.
- Observability frameworks (**LangSmith, Phoenix, OpenLLMetry**) provide post-hoc audit traces of LLM invocations.
- Fact-checking and agent memory architectures (**MemTxn, BioRAG**) check whether claims match citations in a global document corpus.
- Security frameworks (**Macaroons, PCFS**) provide cryptographic capability tokens with contextual caveats.

However, a fundamental systems gap persists across the boundary connecting non-deterministic AI inference to persistent health state mutations:

> **The Inference-Consumption Disconnect:** Existing systems cannot guarantee that a persistent mutation proposal $P$ submitted at $t_3$ is attributable to the *exact governed disclosure projection* actually supplied to the inference instance that produced $P$'s lineage, nor do they atomically revalidate both dynamic governance directives and database dependencies within the commit transaction.

GLHS R3 resolves this disconnect through **Governed Read-to-Write Continuity (GRWC)**, operationalized via an **Exact Inference Consumption Binding**. This document evaluates this mechanism against existing literature, establishes strict non-novelty boundaries, and bounds the defensible scientific claims of the R3 program.

## 2. Theoretical Formulation: The Two-Digest Binding & GRWC Invariant

### 2.1 Formal Invariant Definition

Let:
- $H$: Governed Disclosure Object (Temporal Health State Snapshot / THSS), specifying:
  - $\text{profile\_id}$, $\text{actor\_id}$, $\text{actor\_role}$, $\text{purpose}$, $\text{task}$,
  - $[\text{valid\_from}, \text{expires\_at}]$,
  - active policy version $V_{\text{pol}}$ and consent version $V_{\text{con}}$,
  - evidence manifest $M(H)$ containing disclosed clinical entity IDs,
  - model-visible disclosure projection $\Pi(H)$.
- $I$: Server-owned Inference Context Binding witnessing the exact invocation dispatched to an LLM provider.
- $P$: Persistent Write Proposal generated by or descending from inference $I$.
- $D(P)$: Operation-derived semantic dependency vector required for $P$.
- $S(t)$: Relational database state at time $t$.
- $G(t) = \langle \text{Policy}(t), \text{Consent}(t), \text{Auth}(t) \rangle$: Active governance directives at time $t$.
- $t_c$: Timestamp of atomic database admission transaction execution ($t_3$).

The R3 Commit Kernel admits proposal $P$ into the durable store if and only if:

$$\begin{aligned}
\text{Admit}(P, t_c) \iff \exists H, I: \; & \text{Issued}(H) \\
& \land \text{SuppliedToInference}(I, H) \\
& \land \text{ProposalDescendsFrom}(P, I) \\
& \land \text{ExactDisclosure}(P, I, H) \\
& \land \text{EvidenceCovered}(P, H) \\
& \land \text{DependencyComplete}(P) \\
& \land \text{StateCurrent}(P, S(t_c)) \\
& \land \text{GovernanceCurrent}(P, G(t_c)) \\
& \land \text{DisclosureAdmissibleAtCommit}(H, t_c)
\end{aligned}$$

### 2.2 The Two-Digest Model ($H_{\text{proj}}$ vs. $H_{\text{env}}$)

To eliminate ambiguity between "a valid patient snapshot existed in the database" and "this exact slice of clinical data was presented to the LLM," GLHS R3 introduces a dual-digest cryptographic attestation:

```text
                  +----------------------------------------------+
                  |           Governed Disclosure H              |
                  |  (Full Snapshot, Metadata, Evidence Manifest)|
                  +----------------------------------------------+
                                         |
                                         v
                  +----------------------------------------------+
                  |         Canonical Request Envelope           |
                  |           clara.inference-envelope.v1        |
                  |                                              |
                  |  +----------------------------------------+  |
                  |  | Model-Visible Health Projection Pi(H)  |  |
                  |  +----------------------------------------+  |
                  |  | System Prompt & Template Versions      |  |
                  |  | Actor, Role, Purpose, Task Metadata    |  |
                  |  | Snapshot Identifiers & Manifest Hash   |  |
                  +----------------------------------------------+
                         /                                \
                        /                                  \
     [Hash Projection Slice]                     [Hash Entire Envelope]
              |                                            |
              v                                            v
    +--------------------+                       +--------------------+
    | Projection Digest  |                       |  Envelope Digest   |
    |      (H_proj)      |                       |      (H_env)       |
    +--------------------+                       +--------------------+
```

1. **Model-Visible Health State Projection Digest ($H_{\text{proj}}$):**
   $$H_{\text{proj}} = \text{SHA-256}\left(\text{CanonicalJSON}\left(\Pi(H)\right)\right)$$
   Computed strictly over the normalized, model-visible patient clinical attributes (e.g., active medications, allergy records, recent lab observations) serialized via RFC 8785 (JSON Canonicalization Scheme). It captures exactly what the model was permitted to "see" regarding the patient's health state.

2. **Full Canonical Request Envelope Digest ($H_{\text{env}}$):**
   $$H_{\text{env}} = \text{SHA-256}\left(\text{CanonicalJSON}\left(\mathcal{E}_{\text{req}}\right)\right)$$
   Computed over the complete server-owned request envelope $\mathcal{E}_{\text{req}}$, including system prompts, prompt template version IDs, task/purpose tags, model route configurations, and the disclosure reference. Transient transport metadata (e.g., bearer tokens, provider API keys, ephemeral network request IDs) are strictly excluded.

### 2.3 Creation Point: Pre-Dispatch Server-Attestation

A critical architectural invariant defined in `GLHS_R3_TECHNICAL_DESIGN.md` (§3) and `GLHS_R3_MASTER_SPEC.md` (§3.2) is the **point of binding creation**:
- The authoritative binding record `GlhsInferenceContextBinding` is instantiated by the trusted application server **immediately after final canonical serialization and immediately prior to dispatching the HTTP/gRPC request to the LLM provider**.
- The binding record is initialized with status `PENDING`. Upon successful receipt and canonicalization of the provider completion, the server records the `reported_model_id`, records the completion timestamp, computes an optional `response_digest`, and transitions the binding to `COMPLETED`.
- **Adversarial Invariant:** Neither untrusted clients, human clinicians, nor remote LLM completions can author or manipulate authoritative binding fields (`projection_digest`, `request_envelope_digest`, `snapshot_id`, `actor_id`, `purpose`). Any attempt by a client to submit synthetic binding coordinates is rejected at the gateway.

## 3. Comparative Literature Evaluation

We systematically evaluate the Exact Inference Consumption Binding against the three most prominent adjacent technical paradigms in software engineering, security, and AI systems.

### 3.1 Dimension 1: Prompt Logging & Observability Tools (LangSmith, Phoenix, OpenLLMetry)

#### 3.1.1 Architectural Mechanism
Modern LLM application stacks employ observability and tracing frameworks such as **LangSmith** (LangChain), **Arize Phoenix**, and **OpenLLMetry** (Traceloop / OpenTelemetry GenAI Semantic Conventions). These systems operate as client-side interceptors or middleware SDK wrappers. When an application calls an LLM, the wrapper captures the input messages, prompt templates, system instructions, model parameters, and raw model outputs, formatting them as distributed tracing spans (OTel spans) and exporting them asynchronously to a telemetry backend.

#### 3.1.2 Mechanistic Limitations & Structural Deficiencies
1. **Post-Hoc, Out-of-Band Observability:** Observability frameworks are purely passive listeners. Spans are streamed to an independent analytical store (e.g., ClickHouse, Elasticsearch, or SaaS dashboards) decoupled from the primary application database.
2. **Absence of Downstream Database Gating:** Prompt logging tools provide **zero write admission gating**. When an agent generates a mutation (e.g., updating a patient's EHR dosage), the database transaction executing the write has no mechanism to query or verify the telemetry span. A downstream writer can execute arbitrary database mutations regardless of whether the prompt was logged, omitted, corrupted, or altered.
3. **Malleability and Decoupled Lineage:** In LangSmith/Phoenix, trace IDs are informational identifiers. If an attacker or compromised microservice alters the model's output proposal before writing it to PostgreSQL, or submits a proposal claiming to descend from a different prompt, the database commit engine cannot detect the substitution.
4. **No Concurrency or Governance Awareness:** Telemetry tools cannot revalidate whether patient consent was revoked or whether clinical state drifted between prompt dispatch and database write.

#### 3.1.3 The GLHS R3 Contrast
GLHS R3 elevates the inference trace from an **out-of-band audit record** into an **in-band transactional admission precondition**:
- The binding $I$ is stored in the transactional database.
- The proposal $P$ carries an immutable lineage reference to $I$.
- The database commit kernel (`commit_kernel.py`) enforces $ExactDisclosure(P, I, H)$ inside the same PostgreSQL transaction that applies the mutation under row and advisory locks, failing closed if the binding is missing, altered, uncompleted, or mismatched.

### 3.2 Dimension 2: Source-Citation & Fact-Checking Frameworks (MemTxn, BioRAG, RAGAS)

#### 3.2.1 Architectural Mechanism
In retrieval-augmented generation (RAG) and stateful agent memory, systems such as **MemTxn** (Cui et al., arXiv 2026), **BioRAG / MedBioRAG** (Kim et al., 2025/2026), and **RAGAS** (Es et al., 2024) focus on factual verification and citation faithfulness:
- **BioRAG / MedBioRAG:** Uses dense and hybrid retrieval over medical literature (PubMed, clinical guidelines) and measures whether generated answers align with retrieved passages.
- **MemTxn:** Defines a transaction boundary for agent memory updates, executing an "Ordered PatchTest" that checks whether proposed memory updates cite valid, supporting source passages in the underlying knowledge store.
- **RAGAS:** Calculates algorithmic metrics (faithfulness, answer relevance) by measuring lexical or semantic overlap between generated claims and retrieved context chunks.

#### 3.2.2 Mechanistic Limitations & Structural Deficiencies
1. **Global Source Support vs. Exact Consumed Disclosure:** Citation and RAG-verification frameworks evaluate whether a proposed claim is supported by *some valid source* in the general knowledge base or EHR. 
   - *The Undisclosed Evidence Vulnerability:* Suppose an EHR database contains a historical record indicating "Patient diagnosed with Penicillin allergy in 2018." Suppose further that during the compilation of disclosure $H_1$ for a specific medication order task, this allergy record was **withheld** (e.g., due to task-specific minimization, role filtering, or a temporary redaction policy). If the LLM hallucinates or infers this allergy from parametric memory and proposes an update citing the 2018 record, a source-citation framework (like MemTxn or BioRAG) checks the database, finds the 2018 note, and marks the proposal as **valid and source-supported**.
   - In contrast, from a clinical governance standpoint, this represents an un-governed disclosure breach or un-attested reasoning step: the model generated a state mutation based on information it was never authorized to observe during that session.
2. **Blindness to Prompt Slice Manipulation ($H_{\text{proj}}$):** Source-citation frameworks do not verify what exact prompt slice was visible to the model. If prompt construction accidentally truncates half the patient's active prescriptions, but the model outputs a reconciliation matching the full chart (or vice versa), citation matching cannot detect that the model's actual prompt context was corrupted.
3. **Decoupled from Dynamic Consent & Concurrency:** Source-citation tools verify textual or semantic entailment at the application layer. They do not evaluate whether the patient revoked consent for that specific evidence category while the inference was running, nor do they lock the underlying database records during validation.

#### 3.2.3 The GLHS R3 Contrast
GLHS R3 strictly rejects global source support as a sufficient condition for write admission. Under the GRWC invariant:
- **Evidence Covering Invariant:** $EvidenceCovered(P, H)$ requires that every evidence ID asserted by proposal $P$ must be explicitly enumerated in the manifest $M(H)$ of the disclosed snapshot $H$ that was bound to inference $I$.
- If an evidence item exists in PostgreSQL but was omitted from $H$ (or compiled into a different snapshot $H_2$), proposal $P$ is immediately rejected with `evidence_not_disclosed`.
- GLHS R3 verifies not merely that a statement is "true in the world," but that the proposal is **continuous with the exact bounded projection authorized for that specific inference lineage**.

### 3.3 Dimension 3: Contextual Capability Tokens & Proof-Carrying Authorization (Macaroons, PCFS)

#### 3.3.1 Architectural Mechanism
Decentralized authorization and capability architectures use cryptographically signed tokens carrying contextual restrictions:
- **Proof-Carrying File System (PCFS)** (Garg et al., IEEE S&P 2010): File system requests must accompany formal, machine-checkable constructive proofs in an authorization logic demonstrating that the caller possesses legitimate access rights.
- **Macaroons** (Birgisson et al., NDSS 2014): Bearer cookies constructed using chained HMACs that allow flexible, decentralized caveat attenuation (e.g., restricting valid time windows, allowed IP ranges, authorized API endpoints, and third-party discharges).

#### 3.3.2 Mechanistic Limitations & Structural Deficiencies
1. **Access Authorization vs. Non-Deterministic Transformation Attestation:**
   - Capability tokens answer the question: *"Is Principal $A$ authorized to read Resource $X$ or write to Resource $Y$ under Caveats $C$?"*
   - They do **not** and cannot answer: *"Did a non-deterministic remote neural model actually consume the exact disclosure projection $H$ to produce the specific mutation payload $P$?"*
2. **The Prompt-Decoupling Flaw:** A caller can obtain a valid Macaroon authorizing clinical write operations for patient profile `phr_10029`. The caller can then:
   - Call an LLM with completely fabricated or un-governed prompt text;
   - Modify the LLM's proposed medication dosage in transit;
   - Submit the modified proposal accompanied by the valid Macaroon.
   The Macaroon's HMAC chain verifies perfectly because the caller is authorized and the request satisfies all contextual caveats (time, IP, role). The capability token has no visibility into or cryptographic binding with the model-visible disclosure projection.
3. **Dynamic State Drift (TOCTOU):** Capability tokens are typically issued at session or request initiation. While Macaroons support third-party caveats, standard capability checking does not evaluate whether the underlying clinical entity versions have experienced concurrent write-skew in the database engine during the multi-second LLM execution epoch.

#### 3.3.3 The GLHS R3 Contrast & The Minimal Baseline (E03)
GLHS R3 recognizes that capability tokens are a powerful authorization primitive, but demonstrates that **authorization alone is insufficient for governed AI write continuity**:
- In `GLHS_R3_MASTER_SPEC.md` (§1.3, §7.3) and `GLHS_R3_EXPERIMENT_AND_STATISTICS_PLAN.md` (E03), R3 mandates testing against a minimal capability baseline (`MIN_READSET_TOKEN` / `HMAC_READSET_TOKEN`).
- R3 proves that while an attenuated HMAC token can efficiently transport read-set version bounds, it cannot guarantee full provenance reconstructability, cannot prevent prompt projection drift without embedding full projection digests, and cannot enforce non-downgradable multi-turn human-review lineage without server-side lineage state.
- GLHS R3 binds the **exact model consumption event** to the proposal lineage, bridging the semantic gap between capability authorization and non-deterministic agent computation.

## 5. Strict Novelty Bounds & Non-Novelty Declarations

To satisfy Requirements **SCI-001**, **SCI-002**, **SCI-003**, and **SCI-004**, GLHS R3 explicitly defines what is **not novel** and bounds its central claim.

### 5.1 Definitive Non-Novelty Declarations (Surrendered Claims)

GLHS R3 surrenders and strictly forbids claiming novelty for the following mechanisms and concepts:

1. **Prompt Logging & Post-Hoc Auditing:** Capturing prompts, token counts, model outputs, or execution traces is established systems engineering (LangSmith, Phoenix, OpenLLMetry, OTel). GLHS makes no novelty claim for logging prompts.
2. **Cryptographic Hash Commitments & Pointers:** Computing SHA-256 digests over JSON payloads, hashing request buffers, or using Merkle tree structures is foundational cryptographic art (Merkle 1979, RFC 8785). GLHS makes no novelty claim for hashing data.
3. **Optimistic Concurrency Control (OCC) & SSI:** Validating read sets at commit time, private workspace staging, detecting read-write conflicts, and serializable snapshot isolation were established decades ago (Kung & Robinson 1981, Cahill et al. 2008, Ports & Grittner 2012, TicToc 2016). GLHS makes no novelty claim for database OCC or relational transaction isolation.
4. **Data Provenance Graphs:** Modeling derivation lineages, execution activities, and entity dependencies is mature art (Provenance Semirings 2007, W3C PROV 2013, Linux Provenance Modules 2015, Curcin et al. JBI 2017, Margheri et al. IJMI 2020). GLHS makes no novelty claim for provenance itself.
5. **Purpose-Based Access Control (PBAC) & Usage Control:** Gating data retrieval by declared purpose, role, or task is established literature (Hippocratic Databases 2002, Byun & Li 2008, UCON 2004). GLHS makes no novelty claim for purpose-restricted reads.
6. **Dynamic Patient Consent:** Granular, versioned, revocable patient consent models in health informatics are established art (Kaye et al. EJHG 2015). GLHS makes no novelty claim for dynamic consent models.
7. **Temporal & Bitemporal EHR Storage:** Valid-time vs. transaction-time schemas and snapshotting in medical databases are established (Snodgrass et al., TOKI 2026). GLHS makes no novelty claim for temporal data storage.
8. **Transactional Agent Memory & Belief Commits:** Staging agent beliefs and rolling back failed memory states is concurrent prior art (MemTX 2026, MemTxn 2026, Cordon 2026). GLHS makes no novelty claim for transactional agent memory in general.
9. **THSS Merely as a Data Structure:** The Temporal Health State Snapshot (THSS) is an implementation realization and serialization profile, not an abstract scientific discovery.

### 5.2 The Specific, Unbroken Novelty Claim

The sole, defensible scientific contribution of GLHS R3 is:

> **Server-attested continuous binding of the exact model-visible governed disclosure projection to downstream write admission.**

#### 5.2.1 Deconstruction of the Novelty Claim
1. **Server-Attested:** The binding $I$ is established authoritatively by the trusted application server before external provider dispatch, preventing untrusted clients or LLM outputs from forging consumption coordinates.
2. **Continuous Binding:** The cryptographic link spans the entire lifecycle: from the compiled disclosure snapshot $H$ at $t_1$, through the non-deterministic provider inference $I$ at $t_2$, through human-in-the-loop review (preventing lineage laundering), to write admission at $t_3$.
3. **Exact Model-Visible Governed Disclosure Projection:** The invariant verifies the exact clinical attribute slice presented to the model ($H_{\text{proj}}$) and the canonical envelope ($H_{\text{env}}$), strictly rejecting proposals that rely on undisclosed evidence or truncated context.
4. **Downstream Write Admission:** The binding is enforced by an atomic database commit kernel within the mutation transaction, simultaneously revalidating dynamic consent, policy, and clinical state under strict concurrency locks.

### 5.3 Boundary of Guarantees: What GRWC Does NOT Prove

In accordance with scientific integrity standards, the R3 manuscript must explicitly state what the GRWC invariant does **not** guarantee:
- **No Proof of Clinical Correctness:** GRWC guarantees transactional and disclosure continuity; it does **not** prove that the LLM's recommendation is diagnostically sound or medically effective.
- **No Proof of Model Causal Reasoning:** GRWC proves what was *supplied* to the model; it cannot prove that the model reasoned *exclusively* from that disclosure without relying on parametric training weights, priors, or hallucinations.
- **Trusted Store Assumption:** GRWC assumes the integrity of the application server and the PostgreSQL database engine; it does not protect against a root-level kernel compromise or malicious database administrator.
- **Audited Route Boundary:** GRWC guarantees write admission safety across audited GLHS commit routes; un-audited legacy endpoints that do not route through the commit kernel must be separately protected or retired.
