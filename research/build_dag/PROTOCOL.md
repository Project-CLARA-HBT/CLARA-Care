# Prospective replay of public build graphs

Use the pinned zlib and libdeflate releases configured in the first local Ninja captures. Condition on their default all target at Release optimization. Use the earlier build as historical durations. Collect a fresh clean build per project at four workers. Score identical task durations and prerequisites in a nonpreemptive, homogeneous-machine replay with two, four, and eight slots. Realized durations enter only the event clock, never priority construction. The primary endpoint is replay makespan. Timings in the evaluation capture include whatever resource contention occurred during that build. A replay is not an actual scheduler deployment.

Compare lexical-ready list scheduling, longest historical processing time, and historical critical-path upward rank (homogeneous zero-transfer HEFT priority). Also compare a portfolio selecting the fastest of these three priorities on the historical build. The candidate uses the winning historical list and searches all single pairwise priority swaps on that build. Break ties by retaining the baseline. All methods get the same historical trace, project graph, worker count and up to the same number of schedule evaluations. Report actual planning work and every tie or loss. Give the clairvoyant critical path and work-per-slot lower bound as a diagnostic. Carry the candidate forward only on a strict gain over every runnable comparator in each project at four slots and positive average gain over all six cells. This is development evidence on two projects; a gain would still require comparisons to stronger optimization methods, more external traces and actual builds.
